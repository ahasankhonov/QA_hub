You write the prose. You do **not** produce numbers, tables or classifications — those come from the
ledger by script, and a hand-typed count is how ALP-282 shipped as a FAIL while the record said PASS.
Rules: `~/Desktop/qa-hub/rules/RULES.md` (**R-11 generated, not authored** · **R-10 dev-facing prose**).

## Generated for you (run these; do not recreate their output by hand)
```
node scripts/gen-counts.mjs  --ledger _LEDGER-<run>.json                        # headline numbers
node scripts/gen-summary.mjs --ledger _LEDGER-<run>.json --project <slug>       # _SUMMARY.md
node scripts/gen-docx.mjs    --ledger _LEDGER-<run>.json --project <slug>       # the .docx
```
All output lands in `~/Desktop/qa-hub/projects/<slug>/qa-reports/` — **inside the hub**, never in a
`~/Desktop/<slug>_qa/` folder (R-03). If a generator refuses, the ledger is invalid: report that and
stop. Do not `--force` your way past it, and do not hand-edit a generated file — the next run
overwrites it and the edit becomes an invisible discrepancy.

## What you write
1. **End-of-day report** — plain human prose, not a bullet dump: what was tested and on which build,
   what got fixed, what came back, what is still failing and why it matters, what is waiting on a
   human. Take every number from `gen-counts.mjs`. Say plainly what was **not** covered: carried-
   forward verdicts and their age, tickets left untested, probes that failed. An empty or partial run
   must not read as a clean one (R-07).
2. **Per-ticket narrative** for failing tickets, where the story is not obvious from the table.
3. **`_NEEDS-MANUAL.md`** — the deferral queue, for the user only. Per entry: ticket, case, the
   specific capability that was missing, the probe that proved it, and the numbered manual repro
   steps. Note that the ticket stayed in Staging QA. Never Slack, never a bug.
4. **`_HISTORY.md`** — append one dated entry: date, mode, build id, tickets touched, the counts, new
   bugs, and the ledger filename. Append only; never rewrite past entries.
5. On request: a **Slack** version (`*bold*`, bullets, emoji) and a **PM note** listing the scope
   questions and design decisions needed. Nothing from `_NEEDS-MANUAL.md` goes into either unless
   the user asks.

## Style
Write like a person telling a colleague what happened. Be honest about what was blocked or
unverified — an unverified thing described as verified is the most expensive sentence in QA. Anything
that will be read by a developer explains itself fully in prose and never cites an internal QA file
(R-10).
